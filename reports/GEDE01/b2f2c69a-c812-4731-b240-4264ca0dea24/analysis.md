and signed `long` changes conversion commoning and register allocation despite
their identical 32-bit representation. The all-int variant reached 420 bytes
but regressed to 65.75238%. Narrowing only arithmetic locals or adding explicit
conversion steps did not reproduce retail's conversion scheduling.

## Preserved improvement

`short-mutable-top-left` models the inner top and left boundaries as short
coordinates initialized from x/y and updated with `+= shortInset` at their first
use. Outer vertex arguments continue using the original x/y parameters. This
preserves the low-16-bit arithmetic and signed call values while changing local
lifetimes. It measures 83.7619% in both canonical and relocation-strict objdiff,
an improvement of 0.66666 percentage points over the baseline. The final source
and final raw reports reproduce that candidate.

The generated function is still 436 bytes versus retail's 420 bytes. Register
allocation differs: for example retail saves x/y/depth/inset in r28/r30/r27/r26,
whereas generated code initially uses r27/r28/r26/r23. Retail retains wide inset
sums and repeatedly applies extsh in call argument registers. Generated code
retains narrowed values, adding four net instructions when establishing the
inner top, right, bottom, and left values. See the complete aligned instruction
diff and both raw disassemblies, rather than interpreting the score as a match.

All 20 R_PPC_REL24 relocation types, symbol targets, and zero addends agree in
order. Offsets agree through 0x94. The next retail call relocation at 0xac is at
0xb0 in generated code; the final call is at 0x18c versus 0x19c. The raw readelf
tables and structured comparison include every entry. Relocation-strict objdiff
uses `function_reloc_diffs=name_address`; the matching relocation metadata does
not waive the remaining instruction/offset mismatch.
